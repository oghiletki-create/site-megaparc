# Получение данных из 1С через протокол OData

Источник: статья Infostart **«Работа с 1С через протокол OData»**
(https://infostart.ru/1c/articles/1570140/, 17.12.2021, раздел «Интеграция —
WEB-интеграция»). Текст статьи получен от Олега и законспектирован здесь
полностью; сверен с документацией платформы 1С:Предприятие 8.3. Это единый
справочник для всех интеграций наших систем автоматизации (GO CRM) с 1С клиентов.

## Что такое стандартный интерфейс OData

OData (Open Data Protocol) — открытый веб-протокол для запроса и обновления
данных: операции выполняются HTTP-командами, ответы приходят в XML (atom) или
JSON. Платформа 1С публикует такой REST-интерфейс автоматически, **без единой
строки кода на стороне 1С**. Поддержка появилась в платформе **8.3.5** —
режим совместимости базы клиента должен быть не ниже.

Через OData доступны: планы обмена, константы, справочники, документы, журналы
документов, планы видов характеристик, планы счетов, планы видов расчёта,
регистры сведений, накопления, расчёта и бухгалтерии, бизнес-процессы, задачи.

Зачем это нам: данные без изменений конфигурации клиента, замена
COM-коннектора (работает и с Linux), чтение из веб-приложений (панель
директора, личный кабинет), выгрузка/загрузка, создание объектов, старт
бизнес-процессов.

## Включение на стороне клиента (делает его 1С-ник)

1. База публикуется на веб-сервере через конфигуратор: «Администрирование →
   Публикация на веб-сервере…», с включённой галкой **«Публиковать стандартный
   интерфейс OData»**. Веб-сервер: Apache 2.4 (рекомендуется, кроссплатформенный)
   или IIS. Для доступа из интернета — только с SSL (HTTPS): пароль ходит в
   каждом запросе.
   - Имя публикации — латиницей, без пробелов.
   - Если нет прав администратора ОС или веб-сервер на другой машине — кнопка
     «Сохранить» создаёт файл `default.vrd`, который админ кладёт в каталог
     публикации сам.
2. **Главная ловушка:** после публикации список доступных объектов ПУСТ
   (в типовых конфигурациях 1С активация обычно уже выполнена). Состав задаётся
   серверным методом:

   ```bsl
   Массив = Новый Массив;
   Массив.Добавить(Метаданные.Справочники.Контрагенты);
   Массив.Добавить(Метаданные.Справочники.Номенклатура);
   УстановитьСоставСтандартногоИнтерфейсаOData(Массив);
   ```

   Проверить текущий состав: `ПолучитьСоставСтандартногоИнтерфейсаOData()`.
   Оба метода — только на сервере.
3. Создаётся отдельный пользователь 1С для интеграции с правами только на
   чтение нужных объектов (доступ к объектам ограничивается его ролями).
   Никогда не используем учётку директора.

## Адреса

```
http(s)://<сервер>:<порт>/<имя публикации>/odata/standard.odata/<ресурс>?<параметры>
```

- список коллекций: `…/odata/standard.odata/`
- описание схемы: `…/odata/standard.odata/$metadata`
- формат: `?$format=json` (по умолчанию atom-xml; JSON можно запросить и
  заголовком `Accept: application/json`)
- аутентификация: HTTP Basic (логин/пароль пользователя 1С)

Проверка в браузере:
`http://localhost/smallbusiness/odata/standard.odata/Catalog_Номенклатура?$format=json`

## Имена ресурсов

Схема: `<Префикс>_<ИмяОбъектаКонфигурации>_<Суффикс>` (имя объекта — как в
конфигурации, кириллица сохраняется).

| Объект 1С | Префикс |
|---|---|
| Справочник | `Catalog` |
| Документ | `Document` |
| Журнал документов | `DocumentJournal` |
| Константа | `Constant` |
| План обмена | `ExchangePlan` |
| План счетов | `ChartOfAccounts` |
| План видов расчета | `ChartOfCalculationTypes` |
| План видов характеристик | `ChartOfCharacteristicTypes` |
| Регистр сведений | `InformationRegister` |
| Регистр накопления | `AccumulationRegister` |
| Регистр расчета | `CalculationRegister` |
| Регистр бухгалтерии | `AccountingRegister` |
| Бизнес-процесс | `BusinessProcess` |
| Задача | `Task` |

Суффикс — необязательное уточнение: табличная часть
(`Catalog_ФизическиеЛица_КонтактнаяИнформация`), виртуальная таблица регистра
(`InformationRegister_ЦеныНоменклатуры_СрезПоследних`), `RowType` (строка
табличной части), `RecordType` (запись регистра).

Конкретный объект — по ключу: `Catalog_Контрагенты(guid'xxxxxxxx-…')`.

## HTTP-методы

- `GET` — чтение;
- `POST` — создание объекта;
- `PATCH` — обновление (передаём только изменяемые свойства);
- `PUT` — обновление (передаём ВСЕ свойства сущности);
- `DELETE` — физическое удаление, у клиентов НЕ используем (пометка удаления —
  `PATCH` с `"DeletionMark": true`).

## Параметры выборки

- `$filter` — отбор (язык ниже);
- `$select` — перечень полей (обязательно: без него тянутся все реквизиты);
- `$top` — ограничить число записей; `$skip` — пропустить первые N
  (применяется раньше `$top` независимо от порядка в URL);
- `$orderby=Поле asc, Поле2 desc` — сортировка, можно по дочерним реквизитам
  через `/`: `$orderby=Контрагент/ИНН asc`;
- `$count` — вернуть только размер выборки:
  `Catalog_Товары/$count?$filter=Цена gt 500`;
- `$inlinecount=allpages` — вернуть записи + их количество (`odata.count` в
  JSON); при этом `$skip`/`$top` игнорируются;
- `allowedOnly=true` — вернуть только разрешённое правами; без него запрос,
  задевающий закрытые RLS-данные, падает с ошибкой 401/код 20. Только для
  GET-запросов к наборам сущностей.

### Язык $filter

Логика: `eq, ne, gt, ge, lt, le, and, or, not`; арифметика: `add, sub, mul,
div`; скобки `()` повышают приоритет. Литералы: строки в одинарных кавычках,
`guid'…'`, `datetime'2026-07-01T00:00:00'`.

Строковые функции: `substringof(Str1, Str2)`, `startswith`, `endswith`,
`substring(Str, Нач[, Длина])`, `concat`, `like(Str, Шаблон)` (шаблон как у
ПОДОБНО в языке запросов 1С).

Функции дат: `year, quarter, month, day, hour, minute, second`,
`dayofweek, dayofyear`, `datedifference(Д1, Д2, 'day')`,
`dateadd(Д, 'month', 1)`.

Прочие: `round`, `isof(выражение, 'Тип')`, `cast(выражение, 'Тип')`.

**НЕ поддерживаются:** `length, indexof, replace, tolower, toupper, trim,
years, days, hours, seconds, floor, ceiling`; сравнение с реквизитом типа
ХранилищеЗначения.

Составные типы — только через `cast`/`isof`:

```
$filter=ДокументПрихода eq cast(guid'0d4a79cb-…', 'Document_ПриходнаяНакладная')
$filter=isof(ДокументПрихода, 'Document_ПриходнаяНакладная')
```

Прямое `eq guid'…'` по составному полю всегда вернёт пусто (работает только
для реквизитов типа УникальныйИдентификатор).

Отбор по табличной части — лямбда-функции `any` / `all`:

```
Document_Продажи?$filter=Товары/any(d: d/Цена gt 10000)
```

Примеры:

```
GET …/Document_РеализацияТоваровУслуг
    ?$format=json
    &$filter=Posted eq true and Date ge datetime'2026-07-01T00:00:00'
    &$select=Ref_Key,Number,Date,Контрагент_Key,СуммаДокумента
    &$orderby=Date desc
    &$top=100
```

## Как читать ответ (суффиксы свойств)

- `_Key` — GUID ссылки: отбор по ссылочному полю — `Номенклатура_Key eq guid'…'`;
- `_Type` — диспетчеризационное свойство составного реквизита: строка с
  фактическим типом (`StandardODATA.Document_РасходнаяНакладная`;
  `StandardODATA.Undefined` = Неопределено, значение игнорировать);
- `_Base64Data` — содержимое реквизита типа ХранилищеЗначения в Base64
  (парное `_Type`: `application/octet-stream`, `application/xml+xdto` или
  MIME картинки).

Соответствие типов: Строка→`Edm.String`, Дата→`Edm.DateTime`, целое→`Edm.Int16/32/64`,
дробное→`Edm.Double`, Булево→`Edm.Boolean`, Ссылка→`Edm.Guid`,
Перечисление→`Edm.String`.

## Коды ошибок

HTTP 4XX — ошибка клиента, 5XX — сервера; в теле ответа 1С отдаёт внутренний
код и сообщение. Самые частые у нас:

- **9** — сущность не найдена по ключу;
- **15** — сущность с таким ключом уже существует;
- **19** — HTTP-метод запрещён в данном контексте;
- **20** — нет прав / в выборку попали закрытые RLS-данные без `allowedOnly`;
- **0/21** — возможность или функция не поддерживается;
- **13** — строки табличных частей напрямую не создаются (только через объект);
- **501** — попытка чтения неподдерживаемого типа значения.

## Как это подключается к нашему коду (Node.js)

```js
const base = process.env.ODATA_1C_URL;
const auth = Buffer.from(
  `${process.env.ODATA_1C_USER}:${process.env.ODATA_1C_PASS}`
).toString('base64');

async function odata(collection, params = {}) {
  const qs = new URLSearchParams({ $format: 'json', ...params });
  const res = await fetch(`${base}/${collection}?${qs}`, {
    headers: { Authorization: `Basic ${auth}` }
  });
  if (!res.ok) throw new Error(`1C OData ${res.status}: ${await res.text()}`);
  return (await res.json()).value;
}
```

Переменные на Railway (per instanță, le setează Oleg):
`ODATA_1C_URL`, `ODATA_1C_USER`, `ODATA_1C_PASS`.

Правила для наших выборок: всегда `$select` + `$top` (постранично через
`$skip`), тяжёлые выборки — вне рабочих часов клиента; `allowedOnly=true` на
чтение, чтобы не падать на RLS.

## Чек-лист: что просим у 1С-ника клиента

1. Совместимость базы ≥ 8.3.5; публикация на веб-сервере с галкой OData, за HTTPS.
2. Выполнить `УстановитьСоставСтандартногоИнтерфейсаOData` для нужных
   справочников/документов/регистров (список даём мы; в типовых конфигурациях
   часто уже включено — проверить `ПолучитьСоставСтандартногоИнтерфейсаOData`).
3. Завести пользователя для интеграции с правами «только чтение».
4. Прислать: URL публикации, логин/пароль, список включённых объектов.
5. Проверка с нашей стороны: `GET …/odata/standard.odata/?$format=json`
   возвращает непустой список коллекций; `$metadata` отдаёт схему.
