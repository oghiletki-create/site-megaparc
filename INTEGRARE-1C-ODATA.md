# Получение данных из 1С через протокол OData

Опорный материал: статья Infostart **«Работа с 1С через протокол OData»**
(https://infostart.ru/1c/articles/1570140/, декабрь 2021). Из среды разработки
сам сайт недоступен (сетевая политика), поэтому ниже — конспект по теме статьи,
сверенный со штатной документацией платформы 1С:Предприятие 8.3. Это единый
справочник для всех интеграций наших систем автоматизации (GO CRM) с 1С клиентов.

## Что такое стандартный интерфейс OData

Платформа 1С умеет автоматически публиковать REST-интерфейс ко всей базе —
без единой строки кода на стороне 1С. Обмен идёт обычными HTTP-запросами,
ответы — XML (Atom) или JSON. Для нас это самый дешёвый способ читать данные
из 1С клиента: не нужны обработки, COM или файловые выгрузки.

## Включение на стороне клиента (делает его 1С-ник)

1. База публикуется на веб-сервере (Apache или IIS) через конфигуратор:
   «Администрирование → Публикация на веб-сервере…», с включённой галкой
   **«Публиковать стандартный интерфейс OData»**.
2. **Главная ловушка:** после публикации список доступных объектов ПУСТ.
   Состав задаётся из кода 1С методом
   `УстановитьСоставСтандартногоИнтерфейсаOData(МассивМетаданных)` — либо
   обработкой (у типовых конфигураций есть готовая), либо консолью кода.
   Пока это не сделано, любой запрос вернёт пустой список коллекций.
3. Создаётся отдельный пользователь 1С для интеграции, с паролем и правами
   только на чтение нужных объектов. Никогда не используем учётку директора.
4. Публикация должна быть за HTTPS — пароль ходит в каждом запросе.

## Адреса и формат

```
https://server/имябазы/odata/standard.odata/          — список коллекций
https://server/имябазы/odata/standard.odata/$metadata — полное описание схемы
```

К любому запросу добавляем `?$format=json` (иначе придёт XML/Atom).
Аутентификация — HTTP Basic (логин/пароль пользователя 1С).

Имена коллекций строятся из метаданных:

| Объект 1С | Коллекция |
|---|---|
| Справочник «Контрагенты» | `Catalog_Контрагенты` |
| Документ «РеализацияТоваровУслуг» | `Document_РеализацияТоваровУслуг` |
| Регистр сведений | `InformationRegister_<Имя>` |
| Регистр накопления | `AccumulationRegister_<Имя>` |
| Перечисление | `Enum_<Имя>` |
| Константа | `Constant_<Имя>` |

Табличные части приходят внутри объекта документа; ссылка на элемент —
`Catalog_Контрагенты(guid'xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx')`.

## Чтение: параметры запросов

- `$filter=` — отбор: `Posted eq true and DeletionMark eq false`,
  даты — `Date ge datetime'2026-01-01T00:00:00'`,
  ссылки — `Контрагент_Key eq guid'...'`;
- `$select=` — только нужные поля (обязательно: без него тянутся все реквизиты);
- `$top=` и `$skip=` — постранично, большие таблицы не читаем одним запросом;
- `$orderby=Date desc` — сортировка;
- `$expand=` — сразу развернуть связанный объект (например, контрагента у документа);
- `allowedOnly=true` — вернуть только то, что разрешено правами (без ошибок доступа).

Пример — продажи за период, только нужные поля:

```
GET /base/odata/standard.odata/Document_РеализацияТоваровУслуг
    ?$format=json
    &$filter=Posted eq true and Date ge datetime'2026-07-01T00:00:00'
    &$select=Ref_Key,Number,Date,Контрагент_Key,СуммаДокумента
    &$orderby=Date desc
    &$top=100
```

## Запись (нам почти не нужна, но протокол умеет)

- `POST` на коллекцию — создать объект;
- `PATCH` на `Коллекция(guid'...')` — изменить (пометка удаления — `PATCH`
  с `"DeletionMark": true`);
- `DELETE` — физическое удаление, у клиентов НЕ используем;
- проведение документа — `POST .../Document_X(guid'...')/Post`,
  отмена — `.../Unpost`.

## Ограничения (из статьи и документации)

- Недоступны: отчёты, команды, регламентные задания, пользователи, журнал
  регистрации, внешние источники данных.
- Виртуальных таблиц регистров нет — остатки/обороты готовыми не отдаются,
  считаем сами из записей регистра. Исключение: у периодических регистров
  сведений есть `SliceLast()` / `SliceFirst()` (срез последних/первых).
- Производительность: OData заметно медленнее прямого запроса внутри 1С —
  всегда `$select` + `$top`, тяжёлые выборки только постранично и по ночам.

## Как это подключается к нашему коду (Node.js)

```js
const base = process.env.ODATA_1C_URL;
const auth = Buffer.from(
  `${process.env.ODATA_1C_USER}:${process.env.ODATA_1C_PASS}`
).toString('base64');

async function odata(collection, params = {}) {
  const qs = new URLSearchParams({ $format: 'json', ...params });
  const res = await fetch(`${base}/${collection}?${qs}`, {
    headers: { Authorization: `Basic ${auth}` }
  });
  if (!res.ok) throw new Error(`1C OData ${res.status}: ${await res.text()}`);
  return (await res.json()).value;
}
```

Переменные на Railway (per instanță, le setează Oleg):
`ODATA_1C_URL`, `ODATA_1C_USER`, `ODATA_1C_PASS`.

## Чек-лист: что просим у 1С-ника клиента

1. Опубликовать базу на веб-сервере с галкой OData, за HTTPS.
2. Выполнить `УстановитьСоставСтандартногоИнтерфейсаOData` для нужных
   справочников/документов/регистров (список даём мы).
3. Завести пользователя для интеграции с правами «только чтение».
4. Прислать: URL публикации, логин/пароль, список включённых объектов.
5. Проверка с нашей стороны: `GET …/odata/standard.odata/?$format=json`
   возвращает непустой список коллекций.
